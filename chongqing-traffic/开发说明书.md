## 0. 项目全景：两条线的关系

这个项目有两条并行的线，先搞清楚谁服务谁：

```
工程化线（短期，Phase 0–4）          数据科学线（长期，9 个里程碑）
─────────────────────────────        ─────────────────────────────
把脚本 → 变成规范 CLI 工具           把「看路况」→ 变成「预测路况」
                                ↑
  定时采集脚本 schedule_collect  ←┘
  （Phase 3，是数据科学线的「水龙头」）
```

**核心事实：没有历史数据，就没有预测。** 高德的实时路况 API 只返回「当前这一刻」的路况快照，它不提供免费的历史数据。所以要预测，你必须先用定时采集脚本，持续不断地把实时快照存下来，攒够几个月甚至一年的数据，才能进入后面的建模阶段。

这句话决定了整个项目的节奏：

- **越早开始定时采集，数据越多，预测越早能做。**
- 数据采集（Phase 3 的 `schedule_collect.py`）不是「等做完了再去采集」，而是「工程化一落地就立刻挂上」。

## 1. 关键前提：数据策略

### 1.1 数据是什么

高德交通态势 API 每次返回一个矩形/圆形/道路的**路况快照**，每个路段（road）大致包含：

| 字段 | 含义 | 用途 |
|------|------|------|
| `name` | 道路名 | 定位 |
| `polyline` | 折线坐标（一串 lng,lat） | 画地图 / 空间特征 |
| `speed` | 实时速度（km/h） | **预测目标变量之一** |
| `status` | 拥堵状态（0畅通 1缓行 2拥堵 3严重拥堵 4未知） | 分类目标 / 标签 |
| `direction` | 方向描述 | 区分双向 |

### 1.2 预测什么

交通流预测的常见目标变量，按难度递进：

1. **速度预测**（`speed`）：回归问题，最好做，数据现成。
2. **拥堵等级预测**（`status`）：分类问题，直接可用的标签。
3. **流量预测**（车流量）：需要额外的卡口/线圈数据，高德 API 拿不到，**本项目暂不做**。

建议：**从速度预测切入**。数据现成、指标直观、和后面 ML/DL 全部打通。

### 1.3 采集策略（决定成败）

| 维度 | 建议 | 理由 |
|------|------|------|
| 频率 | 每 5 分钟一次 | 高德免费版有 QPS 限制，且 5 分钟粒度够用 |
| 区域 | 固定几个「命名区域」（渝中、南岸…） | 空间可对比 |
| 时长 | 至少 3 个月，理想 1 年 | 覆盖工作日/周末/节假日/季节 |
| 存储 | 每次一个 JSON 文件，`data/raw/类型_YYYYMMDD_HHMMSS.json` | 对应 Phase 2c |
| 稳定性 | 用系统级定时（Windows 任务计划 / crontab / 云服务器） | 脚本自身 `time.sleep` 不够稳 |

> ⚠️ **最危险的坑**：以为「等数据科学阶段开始再采数据」。到那时你已经白白浪费了半年采集窗口。工程化线一做完（Phase 1/2），就立刻把采集挂上。

### M0 · 项目规范化 — 截止 2027-01-15

**目标**：让仓库达到「陌生人能看懂、能复现」的标准，为后续两年多打地基。

**前置**：无（Phase 0–1 工程化完成即可，其实工程化线已经把这个里程碑大部分做完了）。

**步骤**：
1. 确定最终目录结构：`src/`（代码）、`data/raw`（原始数据）、`data/processed`（清洗后）、`notebooks/`（探索分析）、`config/`（配置）。
2. `.gitignore` 补齐：排除 `data/`、`*.log`、`.env`、`config.local.yaml`、`__pycache__`。
3. `requirements.txt` 或 `pyproject.toml`（已用 pyproject，保持即可）。
4. README 三件套：项目介绍、安装步骤、使用说明（已基本完成）。
5. API Key 环境变量化：确认代码里无硬编码 key，全部走 `--key` 或 `AMAP_API_KEY`。
6. GitHub 仓库就绪，打 tag `v0.1-phase0`。

**交付物**：标准目录 + 干净的 `.gitignore` + 完整 README + 无硬编码密钥。

**验收标准**：
- 一台新机器 `git clone` + `pip install -e .` 后能跑通 `cq-traffic`。
- 仓库里 `grep` 不到任何真实 API Key。

**坑**：API Key 一旦 push 上去，删了也没用（Git 历史还在），要换新 key。所以环境变量化一定要在第一次提交 key 之前做。

### M1 · EDA + Streamlit 面板 — 截止 2027-03-15

**目标**：回答「重庆的交通长什么样」——用数据说话，并做出第一个能演示的交互面板。

**前置**：M0 完成 + **已经攒到至少几周的数据**（这是为什么采集要早挂）。

**步骤**：
1. **数据清洗记录**：开一个 Jupyter Notebook，记录缺失值比例、异常速度（>150km/h 或 <0）、重复采样点，写清楚每个异常怎么处理、为什么。
2. **时间维度分析**：
   - 拥堵时段分布：一天 24 小时，哪些时段拥堵道路占比最高？
   - 早晚高峰特征：早高峰/晚高峰分别几点、持续多久、哪些路段最堵？
3. **空间维度分析**：
   - 常发性拥堵路段热力图：哪些路段「每天都堵」？
   - 用 Folium 叠加热力图层。
4. **Streamlit 面板**：可交互筛选（时间 / 区域 / 拥堵等级），内嵌地图。
5. 部署到 Streamlit Cloud 或本地可演示。

**交付物**：一个可运行的分析 Notebook + 一个可演示的 Streamlit 面板。

**验收标准**：打开面板，能回答「今天早上 8 点渝中区哪里最堵」。

**坑**：
- 数据太短（<2 周）时，周期性结论不可靠。标注「这是基于 X 天数据的初步结论」。
- Streamlit 内嵌 Folium 要用 `st_folium` 或 `components.html`，不是所有 `folium` 输出都能直接 `st.write`。

---

### M2 · 特征工程 — 截止 2027-07-01

**目标**：把「一堆速度快照」变成「模型能学的特征表」。

**前置**：M1 完成，数据清洗逻辑已沉淀。

**步骤**：
1. **时间特征**：小时（0–23）、星期几、是否周末、是否节假日、是否高峰时段（如 7–9、17–19）。
2. **滞后特征**：`t-1`、`t-2`、`t-3`、`t-24`（昨天同一时刻）的速度值。这是时序预测最核心的一类。
3. **滚动统计**：过去 N 小时的均值 / 标准差 / 最大值 / 最小值。
4. **空间特征**：路段长度（从 polyline 算）、路段所在行政区、周边 POI 密度（可用高德 POI 搜索 API）。
5. **天气特征（可选）**：温度、降水，需要额外天气 API（如和风天气）。
6. **特征重要性初步分析**：用树模型跑一遍，看哪些特征最有用。

**交付物**：一个 `build_features.py`（或 `feature_engineering.py`）脚本 + 特征重要性分析文档。

**验收标准**：给定一条路和某个时间点，能自动生成该样本的完整特征向量。

**坑**：
- **数据泄露**：滞后特征必须严格用「预测时刻之前」的数据，滚动统计的窗口不能包含未来。这是 ML 面试高频题，也是新手最常犯的错。
- 训练/验证/测试的划分要用**时间顺序**切（不能用 `train_test_split` 随机切），否则测试集和训练集时间重叠，指标虚高。

---

### M3 · XGBoost 交通流预测 — 截止 2027-09-15

**目标**：跑出第一个可用的 ML 基线，拿到「能比较的指标」。

**前置**：M2 特征工程完成。

**步骤**：
1. **时序划分**：按时间切 train/val/test（例如前 70% / 中 15% / 后 15%）。
2. **XGBoost 基线**：训练 + 交叉验证（`TimeSeriesSplit`，不是随机 KFold）。
3. **LightGBM 对比**：同样数据再跑一遍，对比速度和精度。
4. **评估指标**：MAE、RMSE、MAPE，三个都要报告。
5. **特征重要性可视化**：`plot_importance`。
6. **模型对比报告**：结论 + 下一步方向。

**交付物**：训练脚本 + 指标对比表 + 一份简短报告。

**验收标准**：模型对「明天 8 点某路段速度」的预测，MAPE 达到一个可说的水平（先定个基线，比如 <15%，再逐步优化）。

**坑**：
- 用 `TimeSeriesSplit` 而不是 `KFold`，原因同 M2 的数据泄露。
- 别只盯着 RMSE：速度 20 和 60 的绝对误差含义不同，MAPE 更能体现相对精度。
- XGBoost 本身不会用时间结构，它靠的是你的滞后特征——特征做得好，树模型也能很强。

---

### M4 · LSTM 时序预测 — 截止 2028-01-15

**目标**：引入深度学习，用 LSTM 显式建模时间依赖，和 ML 基线对比。

**前置**：M3 完成；需要提前学 PyTorch 基础（张量、`nn.Module`、`DataLoader`、训练循环）。

**步骤**：
1. **PyTorch DataLoader**：把特征表组织成「序列样本」——每个样本是过去 N 个时间步的速度序列，目标是下一个时间步。
2. **LSTM 模型**：单层 → 多层，加 dropout，逐步调。
3. **训练脚本**：学习率调度、早停（early stopping）、模型保存（`torch.save`）。
4. **与 XGBoost 对比**：相同的数据、相同的 train/val/test 划分，公平对比。
5. **预测可视化**：画「实际 vs 预测」曲线，直观看模型在高峰期的表现。

**交付物**：训练脚本 + 训练好的 LSTM + 对比图。

**验收标准**：LSTM 在相同测试集上和 XGBoost 的指标可对比（允许略差，但要能分析为什么）。

**坑**：
- **数据量不够时 LSTM 会输给 XGBoost**，这是正常的，别灰心。说明里写清楚「当前数据规模下」的结论。
- 记得做**归一化**（速度标准化到 0–1 或标准化），否则 LSTM 难训练。
- 早停要保存「验证集上最好的模型」，不是最后一个 epoch 的。

---

### M5 · Transformer 时序预测 — 截止 2028-03-30

**目标**：上时序 Transformer，完成「ML vs LSTM vs Transformer」三方对比。

**前置**：M4 完成，理解了注意力机制。

**步骤**：
1. **Transformer 实现**：可从零写，也可用现成的时序 Transformer（PatchTST / Informer / Autoformer 的 PyTorch 实现）。
2. **注意力可视化**：画出模型在预测某时刻时，最关注历史里哪些时间步。
3. **三方对比报告**：XGBoost vs LSTM vs Transformer，同样的数据、指标、划分。
4. **模型选择结论**：综合精度/速度/可维护性，选一个「最终部署模型」。
5. **实验报告**：整理成可发布的技术文章（博客 / 知乎 / 公众号）。

**交付物**：Transformer 训练代码 + 注意力可视化图 + 三方对比报告。

**验收标准**：有完整的对比表格和一篇能给别人看的实验文章。

**坑**：
- Transformer 对小数据集容易过拟合，更需要数据量。如果数据不够，它在三方对比里垫底是正常的——如实报告即可，这也是有价值的结论。
- 别一上来就复现 PatchTST 论文全部细节，先用现成库/实现跑通，再逐步理解。

## 4. 跨里程碑的关键决策（提前想清楚）

### 4.1 目录结构演进

```
现在（工程化线）
├── src/cq_traffic/          # 核心代码
└── traffic_maps/            # 地图输出

到 M0 之后
├── src/cq_traffic/          # 核心代码
├── data/
│   ├── raw/                 # 原始 API 响应（不提交）
│   └── processed/           # 清洗后的特征表（不提交）
├── notebooks/               # EDA 与分析
├── config/                  # 配置文件
└── traffic_maps/            # 地图输出（不提交）
```

### 4.2 预测的最小闭环（先跑通再说）

在 M2/M3 之间，先做一个「玩具级」端到端闭环：**取一天数据 → 算滞后特征 → 训练一个 XGBoost → 预测明天 → 看误差**。哪怕指标很差，只要链路通，后面的工作就是「逐步加特征、换模型、调参」，而不是「从零搭链路」。

### 4.3 里程碑不是硬死线

数据是时间的函数，采集晚了后面自然顺延。宁可把日期往后挪，也不要拿「只有 3 天数据」硬凑一个「预测模型」交差——那样的模型没有意义，还会污染你的判断。
